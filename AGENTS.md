# tree

A Claude Code mod (function-hook plugin). `README.md` is the user-facing spec; keep it in step with any behavior change in the same commit.

## Layout

- `hooks/transcript.ts`: pure. Turns transcript JSONL text into compact rows (`Row`: uuid, parent, line, kind, preview text). Knows the transcript's row types; never sees `$`.
- `hooks/tree.ts`: pure. Builds the conversation tree from rows (`buildTree`): parent links, compaction bridges, parallel-tool folding, cycles and missing parents, the newest row and its path.
- `hooks/view.ts`: pure. Filters, search, labels, the visible window around the cursor, row text, the resume command.
- `hooks/policy.ts`: pure. Options (`configFrom`), `/tree` arguments, small text helpers.
- `hooks/register.tsx`: wiring. The `/tree` command, the transcript reader (`$.fs.stat` plus `$.process.spawn` of `tail`), the pane's `ui.render`, `ui.focus` and button handlers, `$.state` and `$.store`.
- `types/index.d.ts`: the mod's types and its `$.state` contract (`PluginState['tree']`). Every `$.state` key the module uses must be declared here.
- `.claude-plugin/plugin.json`: manifest and `userConfig` options. `marketplace.json` makes the repo its own marketplace.
- `scripts/check.sh`: the commit gate (validate, test, typecheck). `scripts/drive.py`: the pty driver for live interactive checks.
- `.claude-plugin/types/` and `tsconfig.json` are generated by Claude Code when it loads the mod from a watched folder. They're gitignored; don't commit or hand-edit them.

## Design (tree)

The mod is a read-only browser over the session's own transcript file. It never moves the engine's position in the conversation: the API has no call for that. Actions hand off to what the engine supports (`$.prompt.fill`, `$.command.run` of `/rewind` and `/branch`, `$.ui.copy`) and say what they do.

- **Transcript location.** `$.session.id()` names the file; the folder is `<config dir>/projects/<slug>/` where the slug is the session root (then the working directory) with every character outside `[A-Za-z0-9]` turned into `-`, and the config dir is `$CLAUDE_CONFIG_DIR` or `~/.claude`. If neither candidate exists the reader looks for `<id>.jsonl` in every project folder. Classic hook events carry `transcript_path`, but a plugin seated above can bypass a mod's classic hooks (seen live on 2.1.310), so the mod does not depend on them.
- **Read-only.** The mod reads transcripts with `$.fs.stat` and `$.process.spawn(['tail', '-c', '+N', path])` and never writes under the projects folder. `$.fs.read` is not used for transcripts: it refuses files over 4 MiB, and long sessions pass 50 MB.
- **Incremental reads.** The reader keeps the byte offset of the last complete line it parsed and reads from one byte before it. The first byte must be the newline that ended that line; anything else (the file shrank, was replaced, or the offset drifted) triggers a full reread. A trailing partial line is left for the next read. Malformed complete lines are counted and shown, never fatal.
- **Tree.** Rows link by `uuid` → `parentUuid`; a `compact_boundary` row (`parentUuid: null`) links through `logicalParentUuid`. Order is file line, never timestamp. Sidechain rows (`isSidechain: true`, older subagent rows) are left out on purpose; subagent transcripts in `<session>/subagents/` are not read. A missing or self parent makes a root; a cycle is broken at its earliest line and reported. A duplicate uuid keeps its first row and is reported.
- **Parallel tool calls are not branches.** The engine writes each tool_use of one API message as its own row and parents each result to its own tool_use, so a raw graph forks at every parallel call. A child subtree that is linear, ends in a leaf, holds only tool-result and attachment rows and assistant rows of the parent's own API message, and starts with an assistant row of the parent's API message or with a tool result, under a parent that is an assistant row, is a fragment (both patterns are in real transcripts: later calls hanging off earlier ones, and results hanging off their own calls): the tree splices fragments, in line order, before the continuing child. Parents are folded bottom-up (latest line first) and fragments are judged on the already folded children, so a chain of three or more calls, and a Skill result followed by its context (meta) and attachment rows, fold too. Only what remains forks.
- **Who sent a row.** Kinds come from the persisted `origin.kind` first, then type, subtype and payload (shapes checked against 2.1.310 transcripts by field names only): a user row with an origin other than `human` (task-notification, plugin, peer) is a `message`, never a prompt; `attachment/queued_command` with origin `human` (or no origin and `commandMode: 'prompt'`) is a prompt with the queued text; `system/local_command` with `<command-name>` is a command, with `<local-command-stdout>` bookkeeping. `isMeta` rows stay meta.
- **Current position.** The engine does not expose its leaf. The mod marks the path to the newest row in the file (by line) as the current path and calls everything else off-path. Right after `/rewind`, until the next message is written, the marker still shows the old leaf; the README says so.
- **Labels** live in `$.store` under `labels:<sessionId>` (uuid → text, trimmed, empty deletes) and are mirrored into `$.state` so the pane redraws. Writes are read-modify-write through one module-level promise chain. No transcript text is stored.
- **What survives what.** The parsed tree is a module variable (too large for `$.state`); a hot reload drops it and `session.start` reloads it when the pane is still open. `$.state` holds the view (filter, query, cursor, mode, notice, a revision counter, load status). Every load carries a generation number and the session id; a result is dropped if either changed while it ran. `/clear` (`session.end` with `reason: 'clear'`) resets the view and the cache.
- **Drawing.** The pane draws only the window of visible rows around the cursor (`bodyRows` less the chrome), so cost per draw is the window plus one projection, which is cached per tree revision, filter, query and labels.
- **Keyboard.** Every action has a Button hotkey; rows are Buttons keyed `row:<uuid>`, and a `ui.focus` hook moves the cursor when the person walks the focus ring onto a row. `j`/`k` and `n`/`p` move the cursor and the ring. Button hotkeys fire while the pane holds the keys even with an Input drawn (seen live on 2.1.310: typing `bravo` into the search field ran `/branch`), so the search and label fields live in modes that draw no hotkey Button at all, and `/rewind` and `/branch` ask before they run. A field and the Button that opens it need different keys: `$.ui.focus({ key })` right after the press landed on the same-keyed Button as it left the tree, and the keys went back to the prompt (2.1.310).
- **Main conversation only.** Subagent turns (`e.agentId`) are ignored.
- **The off switch** is enforced in the loader (`loadOnce` returns before any read), not just in `/tree`: a pane that survives a reload with `enabled: false` is closed at `session.start` and renders an off notice with no actions.
- **Failures are never hidden.** A failed read is its own first line of the pane, ahead of the counts and the query, and the header says the rows are stale. A cached path that no longer exists is rediscovered once per load before the read fails. Graph repairs are counted in the pane and in `/tree status`.
- **Label editing pins its entry** (`view.pending`, with its text in `view.draft`); while it is open the rows draw as text, not Buttons, and the `ui.focus` hook leaves the cursor alone.
- **Headless.** `/tree` in a `claude -p` run answers that it needs an interactive session and reads nothing.
- **No model calls.** Nothing in this mod calls a model or changes the prompt, tools or system prompt. The `/tree` command's one-line output is a transcript row the model reads; keep it short.

## Commands

```sh
scripts/check.sh            # claude plugin validate . && claude plugin test . && typecheck
scripts/check.sh --no-tsc   # when TypeScript isn't available
```

All gates must pass before every commit. A behavior change needs a test in `hooks/*.test.ts` (the `claude-code/testing` kit: `mock.clock`, `mock.store`, `mock.env`, and `on(...)` hooks that stand for the engine beneath the plugin) written first and seen failing for the intended reason, then the change that makes it pass.

To try the mod in a live session: `claude --plugin-dir .` (interactive sessions hot-reload on save), or `claude -p --plugin-dir . "<prompt>"` for a headless run (always loads fresh; hooks that need a terminal won't fire). `claude --debug` logs every skipped hook and refused result.

## API reference

The API is early access and changes between releases; the declarations are the authority, not memory. Grep them by name (`'turn.step'`, `export type ToolCallResult`):

- after the engine has loaded this folder: `.claude-plugin/types/claude-code/index.d.ts`;
- otherwise the newest `claude-code.d.ts` the `plugin-authoring` skill writes under the temp dir (`scripts/check.sh` finds it), plus that skill's `reference.md` and `examples/`.

## Design invariants (apply to every mod built from this template)

- **Main conversation vs subagents.** Events from a subagent's loop carry `e.agentId` (`agent_id` on `classic.*` events). Decide explicitly whether the mod acts on subagents; by default return `next(e)` early for them.
- **Hot reloads reset module variables** (timers included). `register` and `session.start` run again; `$.state` and `$.store` survive. Anything that must persist goes in state or store. Change an atom's `shape` tag when its stored type changes.
- **Never throw out of a hook or timer for reporting.** Logging, status and toasts are best effort. A hook that guards (denies a tool call, drops a prompt) gets a `.catch` that decides fail-open or fail-closed deliberately (`next.called ? next(e) : { deny }`).
- **Headless sessions** (`e.isInteractive === false`, `claude -p`) have no terminal: no panes, `$.ui.notify` fails, `$.session.compact` rejects. Skip or degrade explicitly.
- **Cost and the prompt cache.** Anything that calls a model (`$.model.complete`, `classify`, `fork`, `$.agent.spawn`) is billed to the person. Say what it costs in the README, bound it with options, and don't change the system prompt or tool list per turn (that rewrites the whole prompt cache).

### Engine constraints found the hard way (Claude Code 2.1.29x–2.1.310)

- `$.prompt.submit` is refused from inside a `command.run` hook (it would wait on the turn the hook holds). Submit from a `$.clock.after(0, …)` timer.
- `$.session.compact` rejects while a turn runs and in headless sessions.
- A plugin's submitted prompt never expands `@` mentions; `$.prompt.fill` lets the person send it instead.
- `$.model.fork` replays the main thread's last request, which ends before the turn's final answer: quote the answer into the fork prompt if the fork needs it.
- The engine already prefixes `$.ui.status`, `$.ui.toast` and command output with the plugin name; don't add `tree:` there. `$.ui.log` lines keep the prefix.
- A model `Write` outside the project raises a permission prompt; have the plugin write its own files with `$.fs.write` (it creates directories). `$.fs.write` replaces the whole file; there is no append.
- `turn.step` hooks are async generators in the path of every request: always pass the stream through (`yield* next({ ...e, effort })`). A rewritten `model` must be a full id (`claude-haiku-5-5`); an alias failed with `unrecognized_model`. Changing `effort` per request keeps the prompt cache (Opus, Sonnet, Haiku 5.5); changing `model` rereads everything uncached. The UI keeps showing the session's model and effort, so surface a rewrite with `$.ui.status`.
- `tool.call`: `const r = await next(e); return { ...r, context: [text] }` adds text the model reads after the tool result and the person never sees; `{ deny: reason }` blocks the call. A `tool.call` hook without `.catch` is reported by validate as a gate: give it one that fails open or closed on purpose.
- Haiku 5.5 rejects `temperature`/`top_p`/`top_k`, `budget_tokens` and assistant prefill with a 400. Prices step up 5x above 100K prompt tokens.
- Side calls (forks, completions, subagents, compaction) use the "everything else" prompt-cache bucket (5m on a subscription), not the main conversation's 1h one. Cache reads still count against plan usage.
- Text a hook injects for the model must not talk about the model's thinking or reasoning ("you can't see it", "doesn't count"): Opus 5.5's reasoning-extraction safeguard refused such a request. Phrase it in terms of the reply and the work.
- Don't build on instructions the model can ignore: a gate that "asks" the model to do something first failed live. Enforce in a hook, or give the model the information and let it decide.
- `/clear` is `session.end` with `reason: 'clear'` and no `session.start` after it: reset per-conversation state there.

### Bugs that recur in these mods (check every change against them)

Reviews of relay, defer-queue and prewalk kept finding the same family: a boolean flag left stale by a late event (track the running `turnId` instead), a message lost on a path nobody tested (a refused submit, a release racing a new hold), a timer or async step acting for a run that was cancelled or replaced (guard with a `runId` and re-check after every `await`), state that survived `/clear` or a reload when it shouldn't (or didn't when it should), and engine state copied into the mod's own flags (decide from facts at decision time). Two review rounds of blockers in the same mechanism means change the mechanism.

### Test kit notes

- A hook that answers an op on `$` (`command.register`, `fs.read`, `model.complete`, `ui.toast`, `session.messages`) returns `{ value }` or `{ deny }`; a hook that answers an event (`session.start`, `turn.start`, `turn.complete`) returns the event's result directly.
- One bottom hook per event per test file (a second registration errors). Test files with JSX are `.test.tsx`.
- Use `mock.clock(on)` and `clock.advance`/`settle` for time; there is no `setTimeout`.
- A throwing mock hook is skipped rather than surfacing its error, so test decisions that depend on an error's text as pure functions in `policy.ts`.
- Any helper that receives `$` must be a top-level function: the engine's static check refuses a module that passes `$` to a closure defined inside `register`. `atom({ plugin, key })` takes string literals, not a const.
- The kit accepted a wrong tool-input shape at runtime that `tsc` caught: run the typecheck.

### Live checks

The test kit stands in for the engine; it can't show what the engine really does. Before building on an engine behavior the types don't state, probe it: a throwaway observer mod (`--plugin-dir`) that logs events with `$.fs.write`, and one short live session, with `--model haiku` to keep it cheap. Record the Claude Code version a behavior was checked on. Headless runs (`claude -p`) create transcript folders under `~/.claude/projects/`; run them from a scratch directory.

## Conventions

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`).
- Bump `version` in `plugin.json` for every release users should get. Installs from GitHub run a copy, and `claude plugin update` only replaces it when the version changes. An install whose marketplace is a local clone runs from the clone itself: edit, then `/reload-plugins`.
- MIT licensed: `LICENSE` at the root, and `plugin.json` says `MIT`. Treat the repo as public: no secrets, tokens, session IDs, personal paths or employer-specific details in code, tests, docs or commit messages.
- Don't add Claude or AI attribution trailers to commits.
